# CodeMentor 产品需求文档（PRD）

状态：v0.1（阶段 0 产出） · 维护者：CodeMentor 项目 · 许可：MIT

## 1. 项目背景与核心痛点

AI 编程 Agent（OpenCode、Codex CLI、Claude Code 等）正在替开发者完成越来越多的真实工程工作。随之而来的是一个正在恶化的能力问题——**所有权侵蚀**：

1. 开发者点击"接受"，却不理解**为什么需要这个模块、为什么从这里开始、为什么选这个方案**。
2. 这些"为什么"只存在于转瞬即逝的会话滚动记录里，任务结束后即丢失。
3. 半年后维护这段代码时，没有人（包括当时的 AI）能可靠地回答：**当时还考虑过什么方案？为什么否决了？哪些理由被验证过，哪些只是说法？**
4. 开发者越来越无法**独立做出**同类设计决策——工具替代了执行，也顺带替代了思考的练习机会。

现有工具无法解决这个问题：

| 工具类型                      | 能回答                        | 不能回答                                             |
| ----------------------------- | ----------------------------- | ---------------------------------------------------- |
| 执行日志查看器（session log） | AI **做了什么**（时序动作流） | 为什么这样做、考虑过什么替代方案、理由是否被验证     |
| 代码解释器（code explainer）  | 这段代码**是什么**、怎么运行  | 设计意图与被否决的方案；且其解释全部是**事后生成**的 |
| AI 聊天/导师工具              | 一次性问答                    | 与具体仓库、具体决策、具体代码位置的持久绑定         |

### CodeMentor 与它们的三点本质区别

1. **先声明，后实现（declaration before implementation）**：通过 MCP 工具让 Agent 在写代码**之前**登记设计决策与理由，系统用时间戳保证"先声明后实现"可被验证，而不是事后从日志里猜。
2. **认知来源分级（epistemic provenance）**：每条理由被标记为 `declared`（事前声明的意图）、`observed`（机器可核查的事实：测试/diff/构建输出）或 `rationalized`（事后补写的解释）。三者永不混淆，事后解释永远不会被悄悄升级成"当初的设计意图"。
3. **闭环到代码与练习（anchoring & practice）**：决策通过 CodeAnchor 绑定到具体 commit 与代码位置，并能派生练习题让开发者主动回忆/推演，把"看过"变成"会做"。

## 2. 目标用户

- **P1 被低估的工程师**：1–5 年经验，日常用 AI Agent 完成大量编码，能看懂代码但缺乏独立设计方案的能力与信心。
- **P2 借 AI 重学工程的学习者**：想通过真实项目（而非玩具示例）理解"为什么这样设计"。
- **P3 团队 Tech Lead / 评审者**：需要在评审 AI 辅助产出时，快速看到"AI 声称的理由"与"被验证的事实"之间的差距。

## 3. 核心使用场景

1. **开发中捕获**：开发者照常在 OpenCode 里让 AI 实现功能；AI 通过 CodeMentor 的 MCP 工具在动手前登记决策（问题、选中方案、备选方案、意图主张），实现后自动挂接观察证据（测试运行、diff）。
2. **回顾与理解**：开发者打开 VS Code，在决策树视图里浏览"本任务做了哪些设计选择"；点击代码上的 CodeLens 标记，看到这条代码背后的问题、备选方案与证据状态。
3. **可信评审**：Lead 查看某决策，一眼分辨哪些理由是"声明过的"、哪些是"被证据支撑的"、哪些只是"事后圆场"。
4. **刻意练习**：从真实决策生成练习（如"如果改用备选方案 X，最先崩掉的是什么？"），开发者作答并得到反馈。

## 5. 非功能需求

- **本地优先**：核心功能零网络依赖；不上传用户代码、会话与凭证（仓库内文档与 LICENSE 声明之外无外发数据）。
- **厂商中立**：核心业务逻辑不依赖特定 AI 厂商；Agent 差异被隔离在 Adapter 层。
- **数据可信**：外部输入 100% 过 Zod 校验；时间戳统一 UTC ISO；完整性规则（见 docs/CONTRACTS.md）在写入与查询时强制执行。
- **可测试**：核心引擎全部可在无 VS Code、无真实 Agent 的环境下用 Vitest 验证；集成测试使用真实进程/文件，不用 Mock 冒充。
- **可演进**：存储带版本化迁移；MCP 适配层允许新增 Agent 而不改动核心。

## 6. 明确不属于 v0.1 的功能（Non-goals）

- 云同步、多用户协作、任何形式的遥测上传。
- 除 OpenCode 之外的深度适配（其余 Agent 走通用 MCP，仅保证可用而非最优）。
- 自动从历史日志批量"挖掘"设计决策（无法保证认知来源真实性，与项目核心立场冲突）。
- LLM 自动批改练习（v0.1 只做规则/自评式反馈）。
- 代码生成、代码解释、聊天问答等"代码解释器"类功能。
- VS Code 以外的 IDE 界面。

## 7. 用户故事

- US-1：作为开发者，我让 OpenCode 实现一个功能后，希望它**在动手前**就把"为什么这么做、还考虑过什么"登记下来，这样我不用翻几千行聊天记录。
- US-2：作为开发者，我点开某个函数上方的标记，希望看到这条代码背后的设计问题、选中理由、被否决的方案，以及每条理由的验证状态。
- US-3：作为 Lead，我希望一眼看出某条"AI 给的理由"究竟是事前声明、已被测试支撑，还是事后圆场。
- US-4：作为学习者，我希望系统基于我项目里的真实决策出题，让我练习"换一个方案会怎样"的推演。
- US-5：作为开发者，我希望这一切数据只存在我本机，不上传。

## 8. 功能验收标准（对照第 4 节）

- F1–F6 的详细验收在各阶段开发前细化为可执行测试；本 PRD 只锁定范围与边界。
- 全局底线：任何"声称完成"的功能必须有对应的真实测试记录（docs/TEST_REPORT.md），禁止 Mock 冒充与硬编码演示结果。
- **发布闸门一致性**：任何对外交付声明（README/Release Notes）引用的交付范围必须与本节
  裁定一致；v0.1.0 的对外口径为"F1/F4/F5/F6 交付，F2/F3 顺延 v0.2"。
- 用户文档中的每一条安装/使用命令必须可通过文档自身步骤复现（含扩展 vsix 的打包步骤，
  由 tests/vsix.smoke.test.ts 持续守护）。

## 9. 开源发布注意事项

- 项目名 "CodeMentor" 与既有商业平台 codementor.io 存在名称相近风险；阶段 6 发布前需决策最终名称（改名成本集中在包名 `@codementor/*` 与文档，代码层面可机械替换）。
- 许可证选型见 docs/decisions/（MIT）。
