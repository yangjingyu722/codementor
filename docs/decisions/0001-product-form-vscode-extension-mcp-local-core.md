# ADR-0001：产品形态采用 VS Code 扩展 + MCP + 本地核心服务

- 状态：已接受（阶段 0）
- 日期：2026-10-24
- 影响：整体架构；见 docs/ARCHITECTURE.md

## 背景

CodeMentor 要嵌入"开发者 + AI Agent"的日常工作流，必须同时触达两端：开发者在 IDE 里理解与练习，Agent 在编码前后声明决策与提交事实。约束条件：

1. 不要求用户更换编辑器或 Agent——任何额外切换成本都会杀死采用率。
2. 核心业务逻辑必须可在无 IDE、无 Agent 的环境下被自动化测试。
3. 数据本地优先，不依赖云服务。
4. 深度适配第一个对象是 OpenCode，但不能绑定单一厂商。

## 候选方案

### A. 独立 IDE / IDE 插件化定制

**放弃原因**：维护一个 IDE 是另一个量级的项目；用户切换编辑器的成本极高；与"嵌入现有工作流"的定位直接冲突。

### B. 纯 Skill / 提示词方案（AGENTS.md / system prompt 约定）

即：只写一份提示词，要求 Agent 在编码前输出"设计决策声明"。

**优点**：零安装、零代码。
**放弃原因**：

1. 无持久化——会话结束即丢失，无法积累。
2. 无结构保证——LLM 输出格式漂移，不能作为可校验契约。
3. 无验证——无法核对"先声明后实现"的时间顺序，也就无法区分 declared 与 rationalized（本项目存在的理由）。
4. 方言分裂——每个 Agent 的提示词体系不同，等于按厂商写 N 份逻辑。

### C. 纯日志分析插件（事后挖掘会话记录）

**放弃原因**：日志只能提供**事后视角**。从已完成的代码和对话里反推"设计意图"，得到的全部是 rationalized 主张——这恰是本项目要标记并隔离的东西。时间顺序信息在日志里天然缺失或不可信。此方案可作为未来的补充分析器，不能作为地基。

### D.（选定）VS Code 扩展 + MCP + 本地核心服务

- **VS Code 扩展**承担人机界面：TreeView / CodeLens / Webview 是呈现决策与练习的自然位置，且大多数 Agent 用户本来就工作在 VS Code（或兼容 IDE）里。
- **MCP（Model Context Protocol）**承担 Agent 接入：OpenCode、Codex、Claude Code 均已支持 MCP。一次实现，全部 Agent 可用；Agent 通过**工具调用**在编码前登记决策，使"先声明后实现"成为工作流的强制环节而非道德劝说。
- **本地核心服务**承担全部业务：独立 Node 进程，扩展崩溃不影响数据，Agent 无扩展时也可使用（headless），未来可加 CLI/其他 IDE 前端而无需重写核心。

## 后果与风险

**正面**：核心层可完整测试（阶段化验收的基础）；Agent 生态兼容最大化；本地优先天然满足。

**代价与风险**：

1. 需要维护进程间通信与生命周期（扩展拉起/复用服务进程）——阶段 1 处理。
2. MCP 规范仍在演进——钉住 SDK 大版本，Adapter 层隔离变化。
3. VS Code API 变动——扩展层保持薄，无业务逻辑，迁移面小。

**不可逆性评估**：中等。三块边界清晰，任何一块可单独替换（换 IDE 前端只动扩展层；换 Agent 协议只动 Adapter 层）。
